# NeoST WASM + React Integration Guide

This document explains how the NeoST C++ emulator core integrates with the React web frontend through WebAssembly.

## Architecture Overview

```
┌─────────────────────────────────────────────────────────┐
│                   React Frontend (JavaScript)            │
├─────────────────────────────────────────────────────────┤
│  App.jsx          ControlPanel.jsx      EmulatorContainer.jsx
│     ↓                  ↓                         ↓
└─────────────────────────────────────────────────────────┘
           ↓
┌─────────────────────────────────────────────────────────┐
│              Emscripten JavaScript Bridge                │
├─────────────────────────────────────────────────────────┤
│  wasmLoader.js → neost.js (generated by Emscripten)
└─────────────────────────────────────────────────────────┘
           ↓
┌─────────────────────────────────────────────────────────┐
│            WebAssembly Binary Module                     │
├─────────────────────────────────────────────────────────┤
│  bindings.cpp → Emulator class (C++ bound to JS)
│     ↓
│  WasmEmulator wrapper class
│     ↓
│  neost_core library (C++ emulator)
└─────────────────────────────────────────────────────────┘
```

## Data Flow

### Initialization

```
1. App loads → React mounts
2. EmulatorContainer.jsx initializes
3. wasmLoader.js loads neost.js + neost.wasm
4. JavaScript calls new Module.Emulator()
5. WasmEmulator::initialize() creates Machine object
6. Ready state signaled to React
```

### Emulation Loop

```
React requestAnimationFrame
  ↓
EmulatorContainer.jsx renderFrame()
  ↓
emulator.runFrame()  (C++ WASM)
  ↓
  - Execute 8000 CPU cycles (~1ms at 8MHz)
  - Update video hardware (Shifter)
  - Update audio
  - Render screen to framebuffer
  ↓
JavaScript reads screen buffer from WASM memory
  ↓
ImageData created and drawn to canvas
  ↓
Browser renders frame
```

### User Input

```
User action (keyboard/mouse/joystick)
  ↓
Event handler in EmulatorContainer
  ↓
emulator.setKeyDown(scanCode)  (or mouse/joystick)
  ↓
C++ IKBD controller receives input
  ↓
Emulator processes in next cycle
```

## Key Components

### 1. WASM Bindings (`wasm/bindings.cpp`)

**Purpose**: Expose C++ emulator to JavaScript via Emscripten

**Key class: `WasmEmulator`**

```cpp
class WasmEmulator {
    // Lifecycle
    void initialize();
    void shutdown();
    void reset();
    
    // Emulation
    void step();           // Single cycle
    void runFrame();       // Full frame
    void setRunning(bool);
    
    // Configuration
    void setMachineModel(string);
    void setVideoMode(string);
    
    // Media
    void loadRom(string, ArrayBuffer);
    void loadDisk(string, int, ArrayBuffer);
    
    // Screen data
    uint8_t* getScreenBuffer();     // Access WASM memory
    uint32_t getScreenBufferSize();
    
    // Input
    void setKeyDown(uint8_t);
    void setMousePosition(int16_t, int16_t);
    // ... etc
};
```

**How it works**:
1. Emscripten `EMSCRIPTEN_BINDINGS` macro creates JavaScript wrapper
2. Each C++ method becomes callable from JS
3. ArrayBuffer parameters are passed by reference
4. Screen buffer pointer returned directly (for zero-copy access)

### 2. WASM Loader (`src/utils/wasmLoader.js`)

**Purpose**: Load Emscripten module asynchronously

```javascript
// Usage
const Module = await loadWasmModule();
const emulator = new Module.Emulator();
emulator.initialize();
```

**Features**:
- Singleton pattern (cached after first load)
- Promise-based async loading
- Error handling and logging
- Handles module initialization

### 3. Emulator Container (`src/components/EmulatorContainer.jsx`)

**Purpose**: Main React component managing emulation

```javascript
// Lifecycle
useEffect(() => {
  const Module = await WasmModule();
  emu = new Module.Emulator();
  emu.initialize();
});

// Render loop
useEffect(() => {
  const loop = () => {
    emu.runFrame();
    const buffer = readScreenBuffer();
    drawToCanvas(buffer);
    requestAnimationFrame(loop);
  };
}, [isRunning]);
```

**Responsibilities**:
- Load WASM module
- Create emulator instance
- Manage main emulation loop (60 FPS)
- Read screen buffer each frame
- Handle file loading (ROM/disk)
- Drag-and-drop media support

### 4. Control Panel (`src/components/ControlPanel.jsx`)

**Purpose**: UI controls for emulation configuration

**Provides**:
- Machine model selection (ST, Mega ST, STE, Mega STE)
- Video mode toggle (color/monochrome)
- System information display
- Keyboard shortcuts documentation

**Integration**:
```javascript
handleMachineChange = (model) => {
  emulator.setMachineModel(model);  // Call WASM
};
```

## Memory Management

### WASM Linear Memory Layout

```
┌──────────────────────────────────────────┐
│  0x00000000                              │ Stack (grows down)
├──────────────────────────────────────────┤
│  Emulator state + data structures        │
├──────────────────────────────────────────┤
│  Screen framebuffer (640×400×4 = 1 MB)   │
├──────────────────────────────────────────┤
│  Audio buffers                           │
├──────────────────────────────────────────┤
│  Heap (malloc'd data)                    │
├──────────────────────────────────────────┤
│  ~256 MB free (allows growth)            │
└──────────────────────────────────────────┘
  Total: 512 MB (grows as needed)
```

### Accessing WASM Memory from JavaScript

```javascript
// Get raw pointer to screen buffer
const bufferPtr = emulator.getScreenBuffer();

// Create view into WASM linear memory
const WASM_HEAP = new Uint8ClampedArray(
  Module.HEAPU8.buffer,
  bufferPtr,
  screenBufferSize
);

// Zero-copy: use directly in ImageData
const imageData = ctx.createImageData(640, 400);
imageData.data.set(WASM_HEAP);  // Copy or reference?
ctx.putImageData(imageData, 0, 0);
```

**Performance note**: This is a single memcpy per frame (~2.5 MB for 640×400 RGBA). Acceptable at 50 FPS.

### File Loading

```javascript
// User drops file
const arrayBuffer = await file.arrayBuffer();
const uint8Array = new Uint8Array(arrayBuffer);

// Pass to WASM
emulator.loadDisk("game.st", 0, uint8Array);

// Inside WASM, bindings copy to emulator memory:
// Bus::mountDisk(const uint8_t* data, size_t length)
```

## Performance Optimization

### Frame Rate Management

**Current**: 50 FPS (one logical frame per 20 ms)

```javascript
const renderFrame = () => {
  emulator.runFrame();  // ~5-10 ms on modern CPU
  drawToCanvas();       // ~1-2 ms
  requestAnimationFrame(renderFrame);  // Browser throttles to 60 FPS
};
```

**Result**: Smooth 50 FPS emulation within 60 FPS display refresh

### CPU Optimization

1. **Compile with -O3** (Release build)
2. **Use browser hardware acceleration**
3. **Minimize data copying** (screen buffer)
4. **Frame skipping** (optional, if CPU limited)

### Memory Optimization

- WASM module: ~20 MB (gzipped ~5 MB)
- Runtime heap: ~50 MB average
- Screen buffer: ~1 MB (reused each frame)

## Debugging

### Browser DevTools

1. **Console**: Check for WASM load errors
   ```javascript
   // In browser console
   window.neostEmulator  // Access global instance
   ```

2. **Performance tab**: Profile frame rendering
   - JavaScript execution time
   - WASM computation time
   - Canvas drawing time

3. **Memory tab**: Monitor heap usage
   - WASM linear memory growth
   - JavaScript object allocations

### Common Issues

**"Cannot find module 'neost.js'"**
- Solution: Ensure `public/neost.js` and `public/neost.wasm` exist
- Check: `npm run build:wasm` completed successfully

**"WASM memory access out of bounds"**
- Solution: Increase `INITIAL_MEMORY` in `wasm/CMakeLists.txt`
- Or: Verify screen buffer pointer is valid

**"Emulator runs slowly"**
- Check: Debug build vs Release build
- Enable: Browser hardware acceleration
- Try: Reducing visual effects or frame rate

## Future Enhancements

### Planned Features

1. **Web Workers**: Run emulation in separate thread
   - Main thread: React + UI
   - Worker thread: WASM emulation loop
   - Communication: Message passing

2. **Service Workers**: Cache WASM module for offline
   - First load: Download WASM (~5 MB gzipped)
   - Subsequent loads: Instant from cache

3. **IndexedDB**: Persist save states
   - User creates save state
   - Stored in IndexedDB
   - Loadable across sessions

4. **Multiplayer**: Network play via WebRTC
   - Shared emulation state
   - Peer-to-peer synchronization
